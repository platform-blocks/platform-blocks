# 1.2.0

Two themes: **there is now a single color prop**, and **charts fit the space they are given.**

Six prop names had accumulated for what was largely one job — `color`, `c`, `colorVariant`, `sev`, `tone`, and a `colorScheme` that meant "palette" on two components and "light or dark" on two others. `colorVariant` alone carried four incompatible contracts across the eight components that accepted it, and the split was hiding real bugs: on `Text`, `c="error"` and `color="error"` rendered *different colors*.

**This release is breaking, on purpose.** The old spellings are gone rather than deprecated — the library is new enough that carrying a compatibility layer would cost more than the migration does. A codemod does the rewrite for you.

The second theme is `@platform-blocks/charts`, which stopped drawing at fixed pixel sizes: a chart now measures its container, fills it, and reserves margins from the labels it is about to draw rather than from a constant. [Jump to the charts sections](#charts-fit-the-space-they-are-given).

## `color` is the prop

`color` — with `c` as its shorthand on text-bearing components — now accepts the full vocabulary on every component:

| Form | Example | Resolves to |
| --- | --- | --- |
| Palette token | `color="success"` | that palette, at the shade the context calls for |
| Palette + shade | `color="primary.6"` | exactly that shade |
| Text role | `color="muted"` | `theme.text.muted` |
| Background token | `color="border"` | `theme.backgrounds.border` (Divider) |
| Any CSS color | `color="#2563EB"` | itself |

One helper resolves all of it: `resolveColorProp` in `core/theme`, with `resolveTextColor` / `resolveBg` / `resolveAccentColor` / `resolveLineColor` pinning the shade and token vocabulary per context. It is exported, so app code building its own components can resolve a color prop the way the library does. It replaces roughly a dozen near-identical private resolvers that had each drifted to a different shade default.

`ThemeColor` is exported alongside it and is now the type of every color prop — a palette token, `primary.6` shade syntax, or any CSS color, with editor completion for the tokens. It replaces `AlertColor`, `ToastColor`, `ProgressColor`, and `AccordionColor`, which had drifted apart (`AccordionColor` alone included `tertiary`).

## Colors that were silently discarded

`color` accepted a raw CSS color on Button, Badge, and Chip — and quietly threw it away on nine other components, which looked the value up as a palette key, got `undefined`, and fell back to primary. `<Switch color="#FF0000">` rendered blue. So did `<Switch color="primary.2">`.

Every one of these now takes the full vocabulary, at the shade it already used for bare tokens — so nothing that works today moves:

| | Was accepted | Silently dropped |
| --- | --- | --- |
| `Switch` | 6 bare palette names | raw colors, shade syntax, aliases |
| `Progress` | bare names, `#hex` | `rgb()`/named colors, shade syntax, aliases |
| `Waveform` | 6 hard-coded names | every other palette, shade syntax, aliases |
| `Tabs` | bare names | raw colors, shade syntax, aliases |
| `Accordion` | bare names | raw colors, shade syntax, aliases — fell back to **gray** |
| `Gauge`, `Link`, `IconButton`, `CodeBlock` | bare names, raw colors | shade syntax, aliases |

A cross-component contract test now asserts this table rather than trusting it.

`Pagination` and `KeyCap` still take only palette names — they index several shades of one ramp, which a single color can't supply. Their types say so.

## Fixed along the way

- **`Text`: `c` and `color` disagreed.** `c` resolved a bare palette name to shade 6 and `color` to shade 5, so the same token rendered as two different colors depending on which spelling you reached for. Both now resolve at shade 6 — the higher-contrast neighbour of the base in *both* light and dark, since palettes invert between schemes. `color="success" | "warning" | "error"` on `Text` shifts one shade darker in light mode and one lighter in dark; every other value is unchanged.
- **`Toggle`: precedence was inverted.** `colorVariant` overrode `color`, the opposite of every other component. A `ToggleButton`'s own color also lost to its group's; the child now wins, as it does for `variant`, `size`, and `disabled`.
- **`Timeline`: `color` never reached the resolver.** `<Timeline.Item color="primary">` passed the literal string `"primary"` through to the style.
- **`Highlight`** resolved its wrapped `Text`'s color with its own copy of the lookup, which could land on a different shade than the `Text` inside it.
- **Docs prop tables** dropped the description of any prop whose JSDoc wrapped a `@deprecated` note across lines, and spliced the note's continuation into the description text.
- **`AppShell`: the chrome flashed light on a statically rendered page.** The shell dressed its header, navbar, aside, toc, footer, and bottom bar off the gray ramp behind a `theme.colorScheme` branch. A branch is resolved wherever it runs — in Node, at prerender, where the scheme is always light — so the static markup carried a light hex per chrome surface that no stylesheet could correct, and a dark-mode reader watched the shell sit light until hydration re-ran the branch. Everything around it was already dark at first paint, which is what made it so visible. The steps the shell uses are now published as CSS variables by `createThemeColorVariablesCss`, so the cascade answers the branch before any JavaScript runs. Apps already inlining that stylesheet get the fix with no change; native and apps that have not opted into `colorsAsCssVariables` keep literals. The new `shellChrome` / `shellChromeColors` helpers are exported for app chrome that needs to match.

## Removed

| Removed | Use instead | Where |
| --- | --- | --- |
| `colorVariant` | `color` | Text, Button, IconButton, Checkbox, ControlField, Toggle, ToggleGroup, Divider, Timeline |
| `sev` | `severity` | Alert, Toast, and `toast.show({ … })` |
| `tone` / `hoverTone` / `activeTone` | `color` / `hoverColor` / `activeColor` | MenuItemButton |
| `colorScheme` | `color` | Slider, RangeSlider, Joystick |
| `'danger'` | `'error'` | Menu, MenuItemButton |
| `'info'` as a *color* | `'primary'` | still a valid `severity` on Alert / Toast |
| `Notice` | `Alert` | the component and its `Notice*` types |
| `AlertColor`, `ToastColor`, `ProgressColor`, `AccordionColor`, `SliderColorScheme`, `DividerColorVariant`, `MenuTone` | `ThemeColor` | one type, one vocabulary |
| `ProgressWithCompound` | `Progress` | sub-components are attached to it |
| `CodeBlock` `fileName` / `fileIcon` | `files={[{ name, icon }]}` | |
| `DatePickerInput` `withInput={false}` | `<DatePicker>` | |
| `Tooltip` `multiline` | `width` / `maxWidth` | it was already ignored |
| `PhoneInput` `'UK'` | `'GB'` | the ISO 3166 code |
| `BrandIcon` camelCase names, `resolveBrandName` | kebab-case names | e.g. `google-play` |
| `resolveTokenColor` (Button) | `resolveAccentColor` | |

`AudioPlayer` and `BrandIcon` keep `colorScheme` — theirs genuinely means light/dark.

`c` is **not** removed. It is a documented shorthand alongside `bg`, `w`, `h`, and `ff`, and now a strict alias resolving identically to `color`. Where both are passed, `color` wins; the same is true for `Badge`'s `v` / `variant`.

## Migrating

A codemod ships with the repo:

```
npm run codemod:color-props -- src              # rewrite in place
npm run codemod:color-props -- --dry src        # preview
npm run codemod:color-props -- --check src      # exit 1 if anything is stale
```

It covers `colorVariant`, `sev`, the `tone` family, and `colorScheme`. The rest of the table above is a find-and-replace on a name that appears in few places.

It parses with the TypeScript compiler rather than matching text, so it only touches real JSX attributes and object keys — and it scopes the component-specific renames (`tone`, `colorScheme`) to the components they belong to. Pass `--exclude <fragment>` to skip paths, and it will name any site that sets both spellings rather than guessing which to keep.

## Charts fit the space they are given

Every chart drew at a fixed size — `width={720}` in the docs, `width = 400` in the source — and a container narrower than that number simply clipped it. On a phone, most of the chart was off-screen.

**Omit `width` and a chart now fills its container**, remeasuring when that container changes. A `width` you *do* pass is honoured up to what the box can give it, so a chart can no longer draw wider than the space it is in:

```tsx
<View style={{ flex: 1, padding: 16 }}>
  <LineChart data={data} height={240} />   {/* as wide as the padded box */}
</View>
```

Four new props tune it: `aspectRatio` (height as a fraction of the resolved width), `maxWidth` / `minWidth`, and `maxHeight` / `minHeight`. `maxWidth` is the one radial charts want — it caps a pie or gauge at its natural size in a wide column while still letting it shrink on a phone.

The measurement lives in `withChartAutoSize`, applied at each chart's export, and is exported alongside `useChartAutoSize` so an extension building its own visualisation gets the same behaviour without reimplementing it.

## Margins are measured, not guessed

Every cartesian chart reserved `{ top: 40, right: 20, bottom: 60, left: 80 }` regardless of what it was about to draw. That is a third of the width of a chart in a phone-sized column, and it was still not enough for a category called "Customer Success", which wrapped mid-word inside a 44px label box.

Margins now come from the text that will actually be drawn — tick labels, axis titles, the legend, and the chart title — through `resolveCartesianPadding`, which is exported for extensions building their own axes. A chart labelled `$0`–`$500k` spends less width on its axis than one labelled `1,250,000`, and neither wraps nor clips.

Alongside it:

- **Tick labels no longer wrap mid-word.** Vertical labels stay on one line and ellipsise; horizontal ones take a second line only when the padding reserved for one. "Engineering" was rendering as "Enginee / ring".
- **Axis titles stay on one line.** The title box was pinned at 100px, so "Investment (USD thousands)" stacked into two rotated lines across the plot.
- **Colliding labels are dropped on both axes.** Only the horizontal axis used to thin its labels; a heatmap with 5px rows stacked its day names into a smear.
- **Ticks point away from the plot** on all four edges, instead of always down and to the right — which had put a left axis's ticks *inside* the plot, with each chart cancelling it out in its own offset.
- **A legend pinned to the top starts below the chart title** rather than rendering through it.
- **`estimateChartTextWidth` weights by character class.** A flat per-character average under-reserved for digits and capitals — the characters axis labels are mostly made of — so `$500k` ellipsised inside a box sized for it.

## Axis ticks

- **Tick steps are chosen by proximity, not by rounding up.** A domain of 0–8,800 asked for five ticks got a step of 5,000 and an axis with a single label on it. Both tick generators now share `niceTickStep`, which picks the 1/2/5 × 10ⁿ step closest to the requested density — the same rule d3 uses.
- **No more ticks outside the domain.** `generateNiceTicks` ran half a step past `max`, and the axis drew that label wherever the scale extrapolated to — which is how a `$1000k` label ended up floating above a chart whose data topped out at 820.
- **Charts hand the axis its ticks.** `Axis` accepts `ticks`, so the labels and the gridlines behind them come from one array instead of each deriving its own.
- **A pinned `cellSize` on a heatmap scales to fit** rather than overflowing. Both dimensions scale together, so the cells keep the aspect ratio that was asked for.

The 123 chart demos dropped their hard-coded widths and now demonstrate the responsive default; radial demos pass `maxWidth` instead.

## Sankey labels

A Sankey with more than a handful of nodes was illegible. Node names were drawn *inside* the node rectangle, in white, truncated at ten characters — so "Campus Recruiting" read as "Campus Rec…", a name centred on a 40px node spilled out both sides of it, and any node with a pale fill lost its label into the background entirely.

Labels now sit **beside** the node, in the theme's text colour:

- The first and last columns label outward, into a margin measured from those labels — sources read down the left edge, destinations down the right.
- Everything in between labels toward its own flows, with a halo (the text painted once as a background-coloured stroke, once filled) so it stays readable over any link.
- **Those margins are given up when they get expensive.** On a phone the pair was taking more than half the width and squeezing the diagram into a strip, so below that threshold the first column labels inward like every other column — it points into a gap nothing else wants — and the width goes back to the flows. The right margin is the one kept, because the last column has no gap after it to point into; it also gets a wider cap once it is paying alone.
- Labels are checked for collisions against every other label, not just the ones in their own column, and the bigger node wins. Values are dropped a whole column at a time, so a column never reads "Solar / Wind 32 / Hydro".
- The value follows the name in the secondary colour, and is the first thing dropped when a label runs out of room; the name is truncated only after that.
- Two labels closer together than a line of text no longer print over each other — the lower one is dropped, the same rule the axes use.
- Auto node width moved from 8% of the plot (a 40px slab between every pair of columns) to the d3-sankey range of 10–24px, which is where the width for those labels came from.

## Migration notes

- `Text` renders `color="success" | "warning" | "error"` one shade further from the surface than in 1.1.0. This is the fix for the `c`/`color` split; if you were relying on the old shade, `color="success.5"` reproduces it exactly.
- `ControlFieldContextValue.colorVariant` and `ToggleGroupContextValue.colorVariant` are gone. Both contexts now carry a single `color` with the alias already folded in. These are internal context shapes, not component props.
- `CheckboxStyleProps.colorVariant` is gone; it was already unused.
- `'info'` and `'danger'` no longer resolve as colors. They were spellings of `primary` and `error` with nothing extra behind them. `severity="info"` is unaffected — Alert and Toast map it to the primary palette themselves.
- A theme that defines its own `info` or `danger` palette still works: `color="info"` finds it by name like any other palette.
- `SwitchStyleProps.color` is `ThemeColor` rather than `ColorValue`. Both are string types; the change is completion, not compatibility.
- Charts without an explicit `width` now fill their container instead of drawing at 400px. Pass `width` (or `maxWidth`) where a chart is meant to stay small — a sparkline in a table cell, say.
- Cartesian charts draw more plot and less margin at the same `width`/`height`, because the margins are now measured. Screenshot tests over charts will need new baselines.
- `getColor` from `core/utils` is documented as **web only** — it returns a `var(--platform-blocks-color-…)` reference, which is inert on native. It is unchanged; use `resolveColorProp` for a concrete color on every platform.
